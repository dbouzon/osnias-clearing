02 · Founder, market and framework

Founder, market and regulatory framework

Project founder

Osnias Clearing was conceived, designed, organised and documented by its founder, Denis Bouzon, with 100 % self-funding to date. The project has now reached the stage where it needs support to complement the founder’s skills for the next steps: clean code rework, security, the multi-node demonstrator and audit.

Market: a solution that does not yet exist

Osnias offers companies a netting solution that does not exist today. Multilateral netting is a mechanism proven for decades, but reserved for interbank and market infrastructures: as an order of magnitude, CLS and Clearstream together process around EUR 4,300 billion of notional volume per day, i.e. more than EUR 1 million billion per year. Recurring commercial obligations between companies have no equivalent. The aim is therefore not to take a share of an existing market, but to open this mechanism to inter-company flows.

Regulatory framework and risks

The main risk is regulatory: qualification of the infrastructure and of the clearing token. Pre-assessment is under discussion with the AMF; the files submitted to the CSSF (Luxembourg) and the AFA (Andorra) are awaiting discussion. The sector is waiting for this pre-assessment before any commitment: until then, exchanges with potential node operators remain exploratory.

The following design principles limit risk by construction (details: osnias-clearing.com/faq/):

PrincipleScope
Non-custodialOsnias holds neither user funds nor private keys or seed phrases; collateral is escrowed separately on Ethereum.
No credit, overdraft or leverageExecution invariant: instantaneous net exposure ≤ available collateral; any obligation exceeding it is rejected by the code.
Individualised collateralNo common guarantee fund: risk stays with each participant.
No central novationOsnias is not designed as a CCP; distributed multilateral netting, final qualification to be determined with the authorities.
Node responsibilitiesAdmission, blocking and exit of participants are decided by the node manager, under its local framework.
No PFMI claimNo PFMI certification or compliance is claimed; the architecture refers to it for risk management.

06 · PoC architecture

Two software modules, then validation

The Node Stack is jurisdictional and carries onboarding, local compliance and node-side EVM functions. The Clearing Core is transversal and common to all jurisdictions; Sei remains the reference deployment, with network dependencies isolated in an adapter.

Separation principle. The Node Stack decides who is admitted and applies the local framework. The Clearing Core runs clearing once the participant is admitted. Package 3 stress-tests the integrated system; Package 4 audits it.
Package 1

Jurisdictional Node Stack — Ethereum / EVM

TO DEVELOP ON THE EXISTING EVM FOUNDATION — JURISDICTION-SPECIFIC

Purpose: deliver a testnet node able to admit a company, establish its technical identities and accounts, register its Osnias-ID and operate the required EVM functions under applicable local rules.

  • Company onboarding: KYB/KYC/AML, representatives, beneficial owners, admission statuses and evidence.
  • Business backend: SQL database, API / PHP modules or equivalent, onboarding state management and audit trail.
  • 0x-account provisioning and company ↔ Osnias-ID ↔ node ↔ currency ↔ cycle mapping.
  • Node Registrar, EVM registry, escrow and controller on Ethereum testnet; entry/exit controls and events required by clearing.
  • Node-operator interface: admission, suspension, exit, collateral, alerts and operational status.
  • VPN account / identity provisioning for the future O-POP; physical O-POP deployment remains outside the pre-audit PoC.
  • Local conversion / settlement interfaces prepared as integration points, without imposing one regulatory model across jurisdictions.
Milestone 1 — exit criterionA reference jurisdictional Node Stack works end-to-end on testnet: onboarding → 0x accounts → Osnias-ID → EVM, with logs and node-operator interface.
Package 2

Common Clearing Core — Sei reference deployment

EXISTING TESTNET DRAFTS — CLEAN REWORK, INTEGRATION AND EXTENSION

Purpose: build the common transversal clearing structure, independent of node-local law and replicable for each currency.

  • Multilateral netting engine, canonical clearing ledger and consistency invariants.
  • Three chambers per currency: 1W, 4W and 13W, each with cycle states, MINT / BURN / P2P / CLEAR rules and a dedicated end-user interface.
  • 1W / 4W / 13W time oracles and clearing-side solvency oracle; redundancy, freeze and recovery policies.
  • Clearing-side Osnias-ID and mapping to admitted nodes.
  • Clearing-side ISO 20022: mapping of Osnias events, orders, confirmations, statuses and error handling.
  • Sei ↔ Ethereum cross-layer reconciliation, divergence detection and fail-closed behaviour.
  • Core built on standard EVM primitives with a Sei adapter; future portability and migration / multi-deployment without rewriting business logic.
  • Clearing-side O-POP interfaces and specifications; physical O-POP installation takes place after Package 5, during industrialisation.
Milestone 2 — exit criterionThe common Clearing Core runs all three 1W / 4W / 13W horizons on testnet, with chamber interface, netting, oracles, ISO 20022 and reconciliation operational.
Package 3

Integration, Stress Tests & Demonstration

SYSTEM VALIDATION — NOT A THIRD BUSINESS MODULE

Purpose: connect several Node Stacks to the Clearing Core, run complete cycles and expose the system to nominal, load and failure scenarios before audit.

  • Demonstrator with at least three nodes and several simulated participants.
  • Complete 1W / 4W / 13W cycles and flow datasets of different sizes.
  • Load stress: number of obligations, event frequency, state changes and cycle windows.
  • Adversarial scenarios: insufficient collateral, suspended participant, invalid messages, out-of-window operations.
  • Sei / Ethereum desynchronisation, delayed or unavailable oracle, connection loss, latency and recovery.
  • Systematic validation of fail-closed behaviour, logs, evidence and recovery procedures.
  • Measurement of the netting rate and production of reproducible metrics for the audit package.
Milestone 3 — exit criterionSeveral multi-node cycles are executed and documented; failure and stress scenarios are reproducible; no known critical issue remains open before audit.
Package 4

Security Audit

AUDIT READINESS → INDEPENDENT AUDIT → REMEDIATION → RE-TEST
  • Freeze of the code and reference baseline.
  • Audit package: architecture, specifications, invariant list, threat model, tests, coverage, procedures and Package 3 evidence.
  • Final security hardening: static analysis, fuzzing, dependencies, access controls, DoS and attack surfaces.
  • Independent audit of smart contracts and critical components within the agreed scope.
  • Remediation plan, fixes and auditor re-test.
Milestone 4 — exit criterionIndependent audit report delivered; vulnerabilities addressed; remediation re-tested; audited baseline frozen for the complete regulatory filing.

PoC funding architecture

A milestone may be funded by one or several contributors: public grant, private co-funding or industrial partner. A contributor may participate in one tranche or several, allowing the PoC to be funded progressively without requiring a single funder.

For strategic private co-funders, a later equity investment in the future operating company may be negotiated separately. PoC funding and equity investment remain distinct transactions; participation in the PoC does not automatically confer equity rights.
