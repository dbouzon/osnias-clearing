COORD Pilot

COORD Specification 1.0 · moteur coordengine

Prise en main

Cette interface pilote le service local COORD Pilot (MVP) : un orchestrateur de missions d'équipe d'IA conforme à COORD Specification 1.0, avec des adaptateurs simulés uniquement. Aucune donnée réelle n'est échangée.

Collez d'abord le token local affiché dans la console au démarrage du service (il est régénéré à chaque démarrage, jamais journalisé). Renseignez-le dans l'écran Tableau de bord.

Déroulé d'une mission en 6 étapes

  1. Création : référence d'issue, deux adaptateurs simulés, exécutant et réceptionnaire distincts (N-05), plafonds de budget.
  2. Exécution : l'exécutant démarre la mission (état PLANIFIEE → EXECUTION).
  3. Soumission : livrable + révision (40 hex) + empreinte de preuves SHA-256 (64 hex) → DECISION_ATTENDUE.
  4. Réception : verdict ACCEPTEE / REFUSEE / A_CORRIGER rendu par le réceptionnaire uniquement, avec référence obligatoire.
  5. ACK : l'exécutant acquitte sur empreinte inchangée (N-13 : un verdict périmé est refusé).
  6. Clôture : réservée à l'autorité humaine (session locale, N-14).

Légende des états

PLANIFIEE → EXECUTION → DECISION_ATTENDUE → ACCEPTEE/EN_CORRECTION/REFUSEE → ACK_RECU → CLOTUREE. Toute transition hors table fermée est refusée avec motif.

Rôles

EXECUTANT (exécute, soumet, acke) · RECEPTIONNAIRE (rend le verdict, jamais la même identité que l'exécutant, N-05) · PILOTE (l'autorité humaine locale : arrêt, reprise, clôture — jamais dérivable d'un corps de requête).

Suivi du cycle

Transition normative
Le rôle n'est jamais pris depuis cette page côté serveur : il est résolu depuis l'enregistrement de la mission. Le champ « role » d'une requête forgée est ignoré (S4). Les cibles de verdict valident la référence obligatoire du verdict.

Budgets

Consommation par mission
IssueÉtatBudget (appels consommés/plafonds)

Le contrôle budgétaire a lieu avant tout appel d'adaptateur : un plafond dépassé bloque la transition, motif journalisé, aucune action externe (R3). Un adaptateur sans plafond n'a jamais le droit d'appeler (fail closed). Les jetons sont déclarés par l'adaptateur simulé ; le coût monétaire est un indicateur simulé.

Arrêt / levée (autorité humaine)

Arrêt effectif du pilote
Levée de l'arrêt

L'arrêt du pilote est une commande de l'autorité humaine, journalisée ARRET_PILOTE, DISTINCTE des écarts auto-déclarés ECART (N-20). Pendant l'arrêt, toute transition est refusée avec motif explicite, l'état machine reste intact. À la levée, la reprise passe exclusivement par le dispositif normatif N-16/N-17.

Arbitrage / reprise (N-16/N-17)

Divergence simulée entre copies

En cas de divergence, github fait foi (N-16), les champs divergents et les empreintes des deux copies sont journalisés. La reprise n'exécute que si le head vérifié correspond (N-17) ; sinon refus « sha_head divergent ».

Sécurité locale

Contrôles
  • S1/S2 : sans token ou token invalide → 401 journalisé, aucune transition.
  • S3 : le service n'écoute que sur 127.0.0.1 ; toute autre adresse refuse de démarrer.
  • S4 : le rôle PILOTE n'est dérivable que de la session locale authentifiée.
  • S5 : habilitations vides ou mal formées → démarrage refusé (fail closed).
  • R1 : toute transition hors table fermée est refusée avec motif explicite.
  • R3 : budget vérifié avant tout appel ; R4 : arrêt humain effectif ; R6 : verdict périmé refusé.

Chaque refus affiché ici porte un identifiant de trace qui se retrouve dans le journal local de la mission.
