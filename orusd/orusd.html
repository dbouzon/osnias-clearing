ORUSD

A token designed for direct account-to-account clearing

ORUSD is a USD-denominated clearing register token. Its design prioritizes direct P2P circulation between EOA accounts, controlled minting and burning, traceable oracle requests, non-replayable external proofs and final settlement under manager authority.

03 · Technical Role

A clearing register, not a market token

ORUSD is designed for one specific function: representing and transferring a clearing unit between user accounts. Its design does not seek to reproduce the functions of a market token, a lending product or a custody infrastructure.

Clearing

Direct transfer

The normal operational path is a direct transfer from one user EOA account to another user EOA account.

Controlled supply

Explicit mint / burn

Supply changes only through explicit mint or burn paths under manager control, either manually or following a valid oracle request.

Network locality

Local production on Sei

The production model provides for a Sei-native ORUSD, with no bridge, OFT, wrapping, migration or balance continuity from Sepolia.

Canonical state. Ethereum Sepolia is the public reference and test environment. The intended production deployment is separate on Sei EVM. Sepolia balances, proofs and administrative operations create no production entitlement on Sei.
04 · P2P Circulation

Gross debited / net received model

For an ordinary user transfer, the sender is debited the stated gross amount. The protocol deducts 0.15% within that amount and credits it to the feeRecipient; the beneficiary receives the net balance.

1,000.000000 ORUSD

Gross amount requested by the sender.

1.500000 ORUSD

0.15% protocol fee credited to the feeRecipient.

998.500000 ORUSD

Net amount received by the beneficiary.

Transfer invariant. For an ordinary user transfer: sender debit = beneficiary credit + feeRecipient credit. The fee mechanism creates no additional ORUSD.

Permitted circulation

  • EOA → EOA.
  • Gross amount ≥ 0.501 ORUSD.
  • Fee rules apply.
  • Restricted recipient rules apply.

Disabled paths

  • Ordinary transfer to a smart contract rejected.
  • approve() disabled.
  • transferFrom() disabled.
  • Minting to a smart contract is not part of the reference model.
05 · Oracle & Settlement

The oracle attests. The manager settles.

An authorized oracle cannot directly create or destroy ORUSD. It submits a MINT or BURN request based on an identifiable external proof. The request becomes visible on-chain before any supply change.

1 · Attestation

An authorized oracle observes or validates an external event and creates an on-chain request.

2 · Pending

The request includes type, account, amount, external reference and timestamp. It remains executable for 24 hours.

3 · Settlement

Only the manager can execute or reject the request. An expired request can no longer be executed.

Oracle authority

Request only

The oracle can attest and request; it cannot settle or directly modify supply.

Anti-replay

Single-use proof

The same external clearing reference can create only one ORUSD request. Rejection does not release the proof for reuse.

Finality

Terminal status

An executed or rejected request retains an identifiable final state in the audit history.

06 · Collateral & Segregation

USDC as collateral, outside ORUSD custody

The ORUSD specification contemplates USDC as the sole collateral asset. This collateral is neither received, held nor managed by the ORUSD contract. Deposits and lending positions remain within infrastructures operated by independent partners.

Collateral asset

USDC

USDC is the collateral asset contemplated by the ORUSD architecture. ORUSD itself does not hold this collateral.

Partner lenders

External custody

Lending partners remain responsible for their deposit, custody or escrow mechanisms, risk management and collateral contracts.

Structural separation

No unilateral client access

The design requires that ORUSD have no unilateral authority to withdraw a client’s collateral from a partner infrastructure.

Clearing–custody segregation. The ORUSD register and client collateral are distinct domains. A collateral event may produce a clearing instruction through the oracle, but it does not transfer custody of the collateral to the ORUSD contract.

08 · Security

Explicit trust boundaries

Supply

No hidden path

Supply creation and destruction must remain limited to explicitly defined and authorized functions.

Oracle

Separation of powers

Compromise of an oracle alone must not be sufficient to create or destroy ORUSD.

Proofs

Anti-replay

The same external proof cannot produce a second ORUSD request.

P2P accounting

Conservation

An ordinary transfer redistributes existing ORUSD between the beneficiary and the feeRecipient without fee-induced inflation.

Collateral

Asset segregation

Compromise of the ORUSD register must not provide access to client collateral held by a partner.

Production

Privileged-key security

Production privileged keys must be treated as critical authorities and protected by the published mainnet security architecture.
